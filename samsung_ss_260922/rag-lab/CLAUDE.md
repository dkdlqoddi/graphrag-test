# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 프로젝트 성격

PDF → 파싱 → 청킹 → 임베딩·적재 → 검색·생성의 각 단계를 **화면에 그대로 드러내는 것**이 목적인
교육용 naive RAG 앱이다. 성능보다 "무엇이 왜 이렇게 되는지 보이는가"가 우선이다. 단계를 감추거나
자동화로 합치는 변경은 이 목적에 어긋난다.

UI 문구·주석·로그·오류 메시지는 전부 한국어다. 모든 `.py`는 `# -*- coding: utf-8 -*-` 로 시작하고
모듈 docstring 에 그 모듈이 내린 판단의 근거를 적는 문체를 따른다.

## 실행

```
pip install -r requirements.txt     # chromadb, pypdf 뿐. 나머지는 표준 라이브러리
run.bat                             # 또는 python app.py             — 화면  127.0.0.1:8765
run_mcp.bat                         # 또는 python mcp_server.py      — MCP   127.0.0.1:8000/mcp
                                    #     python mcp_server.py --stdio
```

`app.py:check()` 가 chromadb · pypdf · `OPENAI_API_KEY` 세 가지를 먼저 확인하고, 빠진 것이 있으면
서버를 띄우지 않는다. 서버는 `http://127.0.0.1:8765/` 이고 브라우저가 1초 뒤 자동으로 열린다.

`mcp_server.py` 는 같은 것을 확인하되 **막혀도 서버를 연다**(파싱·청킹·저장소 보기는 키 없이도
되므로). 포트는 화면과 나눠 둔다 — 둘을 같이 띄워 놓고 쓸 수 있어야 한다. 점검 결과를 stdout 에
적지 않는 것이 중요하다 — 아래 MCP 항목 참고.

**콘솔 인코딩**: PowerShell 기본 코드페이지(cp949)에서 한글 출력이 `UnicodeEncodeError` 로 죽는다.
`run.bat` 은 `PYTHONUTF8=1` 을 넣어 준다. 직접 실행하거나 스크립트를 돌릴 때도 붙일 것:

```
PYTHONUTF8=1 PYTHONIOENCODING=utf-8 python app.py
```

## 테스트

테스트 프레임워크도 테스트 파일도 없다. 확인은 임시 스크립트로 한다(프로젝트 밖 temp 폴더에 두고):

```
PYTHONUTF8=1 python -c "import sys; sys.path.insert(0,'.'); from lab import llm; print(llm.generate('한 문장으로: RAG 란?'))"
```

MCP 서버는 두 전송을 따로 확인한다. HTTP 는 띄워 두고 두드린다:

```
curl -H "Content-Type: application/json" -H "Accept: application/json" \
     -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' http://127.0.0.1:8000/mcp
```

stdio 는 JSON 한 줄씩을 stdin 으로 흘려 넣는다. 응답도 한 줄에 하나씩 나온다:

```
PYTHONUTF8=1 python mcp_server.py --stdio < requests.jsonl > out.jsonl 2> log.txt
```

`requests.jsonl` 의 첫 줄은 `initialize` 여야 한다. 진행 로그는 `log.txt`(stderr) 로 간다 —
`out.jsonl` 에 JSON 이 아닌 줄이 섞여 있으면 어딘가에서 stdout 으로 인쇄한 것이다.

파이썬으로 두드릴 때 `urllib` 은 프록시 환경변수를 따르므로 `build_opener(ProxyHandler({}))` 로
비켜 두는 편이 안전하다.

저장소를 비우려면 `POST /api/reset`, 또는 `from lab import store; store.reset()`.
파일까지 지우려면 `store.wipe_files()`.

## 구조

### 창구가 둘이다 — 화면과 MCP

같은 기능을 여는 곳이 둘이고, 둘 다 같은 `lab/*` 모듈을 부른다.

```
app.py        → lab/web.py        HTTP · /api/*             사람이 브라우저로 본다  :8765
mcp_server.py → lab/mcp_tools.py  도구 12개                 모델이 도구로 부른다
                lab/mcp_proto.py  JSON-RPC 2.0 + stdio 전송
                lab/mcp_http.py   HTTP 전송 (POST /mcp)                             :8000
        둘 다 → lab/pipeline.py   검색 한 번이 지나는 길
```

**검색의 얼개는 `lab/pipeline.py` 한 곳에만 둔다.** 재작성 → HyDE → 두 열 검색 → 재정렬 →
하이라이트 → 생성 → 되먹임의 순서와 그 사이의 규칙(아래 각 항목)을 두 벌로 나눠 두면 한쪽에서만
지켜지고 다른 쪽은 조용히 어긋난다. `web._api_search` 는 요청을 풀어 넘기는 껍데기이고,
`mcp_tools.search` 도 마찬가지다. 검색 동작을 고칠 일이 생기면 `pipeline.py` 를 고칠 것.

부르는 쪽마다 다른 것은 **진행 상황을 어디에 적느냐**뿐이라 그것만 `log` 로 받는다 — 화면은
`print`, MCP 는 stderr.

**두 서버는 상태를 공유하지 않는다.** 서로 다른 프로세스라 `web.STATE` 와 `mcp_tools.STATE` 가
따로 있다. 함께 보는 것은 `chroma_db/` 뿐이고, 둘을 동시에 띄워 양쪽에서 적재하면 같은 SQLite
파일을 두 프로세스가 쓰게 된다 — 교육용으로는 한 번에 하나만 띄우는 것을 전제한다.

#### MCP 에서 지킬 것 (`lab/mcp_proto.py`)

SDK 를 쓰지 않고 직접 구현했다. `lab/web.py` 가 `BaseHTTPRequestHandler` 를 직접 쓰고
`lab/llm.py` 가 `urllib` 로 OpenAI 를 직접 부르는 것과 같은 이유다. 다루는 메서드는 네 개뿐이다
(`initialize` · `tools/list` · `tools/call` · `ping`).

**말과 전송을 나눠 둔다.** `dispatch()` 는 메시지 하나를 받아 응답 하나를 **돌려줄 뿐 아무 데도
보내지 않는다.** 보내는 일은 전송이 한다 — `mcp_proto.serve_stdio()` 와 `mcp_http.serve_http()`.
같은 `dispatch()` 를 둘이 함께 쓰므로 어느 쪽으로 붙어도 같은 답이 나온다. 새 메서드를 더할
자리는 `dispatch()` 한 곳이다.

- **stdio 에서 stdout 은 프로토콜 전용이다.** 한 줄이라도 다른 글이 섞이면 클라이언트가 연결을
  끊는다. 그런데 이 앱은 진행 상황을 `print` 로 알리도록 되어 있고 chromadb·pypdf 도 제 사정을
  출력한다. 도구를 실행하는 동안 stdout 을 stderr 로 돌려 두는 `quiet()` 가 그래서 있다 —
  **빼지 말 것.** HTTP 전송에서는 stdout 이 프로토콜과 무관하므로 걸지 않는다
  (`protect_stdout=False`). `contextlib.redirect_stdout` 은 전역을 바꾸는 장치라 요청이 겹치는
  HTTP 에서는 오히려 위험하다.
- **`id` 가 없는 메시지(알림)에는 답하지 않는다.** `notifications/initialized` 에 응답을 보내면
  클라이언트가 짝 없는 응답을 받는다. `dispatch()` 는 그때 `None` 을, HTTP 는 `202` 를 돌려준다.
- **도구가 실패한 것은 JSON-RPC 오류가 아니라 `isError` 다.** 프로토콜이 깨진 것과 도구가 실패한
  것은 다르다. 후자는 모델이 읽고 다음 수를 고를 수 있게 한국어 설명을 본문에 담아 돌려준다
  (`ToolError`). 프로토콜 오류는 `-32601` · `-32602` 로만 낸다.

#### HTTP 전송에서 지킬 것 (`lab/mcp_http.py`)

`POST /mcp` 하나만 실제로 말을 주고받는다. 나머지는 **열지 않는다는 것을 분명히 말한다.**

- `GET /mcp` → **405**. 서버가 먼저 말을 거는 SSE 통로를 열지 않는다. 규격은 SSE 를 허용하지만
  우리 진행 로그는 서버 창(stderr)에 적히는 편이 실습에서 낫고, 오래 걸리는 도구도 클라이언트가
  기다려 주면 그만이다.
- `DELETE /mcp` → **405**. **세션(`Mcp-Session-Id`)을 만들지 않는다** — `mcp_tools.STATE` 가
  모듈 전역이라 접속마다 따로 들고 있을 것이 없다(화면이 브라우저 탭 여럿에게 STATE 하나를
  보여 주는 것과 같다). 세션 id 만 나눠 주고 상태는 공유하면 나뉜 척하는 거짓말이 된다.
  세션을 진짜로 나누려면 STATE 부터 접속별로 갈라야 한다.
- **`Origin` 을 확인한다.** 로컬에 열린 서버는 아무 웹페이지나 브라우저를 시켜 두드릴 수 있다
  (DNS 리바인딩). localhost 가 아니면 403 이고, `Origin` 이 아예 없는 요청(브라우저가 아닌
  클라이언트)은 그대로 받는다. 주소를 `0.0.0.0` 으로 넓히지 말 것.

#### MCP 도구의 결과는 글이다 (`lab/mcp_tools.py`)

화면에서는 브라우저가 JSON 을 받아 카드·막대·하이라이트로 그렸다. MCP 에서는 **결과 자체가
화면이어야 한다** — 모델이 읽는 것은 글뿐이다. 그래서 도구는 JSON 을 그대로 돌려주지 않고
한국어 설명문을 짓는다. 유사도 옆에 왜 그 조각이 뽑혔는지를 적고, BM25 가 0건이면 그것이 왜
버그가 아닌지를 적는다. **결과를 JSON 덤프로 바꾸지 말 것** — 숫자만 넘기면 이 앱의 목적이
사라진다.

본문은 `config.MCP_SNIPPET_CHARS` 에서 자른다. 화면은 스크롤하면 그만이지만 여기서는 청크
원문이 그대로 모델의 문맥을 차지한다. 전문이 필요하면 `show_chunks` 로 따로 청한다.

도구는 `TOOLS` 목록에 이름·설명·입력 스키마·함수를 한 줄로 묶어 둔다 — **새 도구는 여기 한 곳만
고치면 `tools/list` 에 나온다**(화면의 `chunking._FN` + `config.STRATEGIES` 처럼 두 곳을 고칠
필요가 없다). 되돌릴 수 없는 도구(`reset_store`)는 `confirm` 을 받는다.

### 단계 사이의 전달

`lab/web.py` 의 모듈 전역 `STATE = {doc, name, chunks, strategy, size}` 가 ①②③ 단계를 잇는다.
**파싱 결과와 청크는 메모리에만 있고, 디스크로 넘어가는 것은 ③ 적재 결과(`chroma_db/`)뿐이다.**
그래서 서버를 재시작하면 "적재된 청크 N개"는 남아 있는데 문서·청크 화면은 비는 상태가 정상이다.
`GET /api/status` 는 새로고침 후 화면을 이 상태 그대로 복원하기 위해 존재한다.

서버는 `ThreadingHTTPServer` + `BaseHTTPRequestHandler` 직접 구현이다. 정적 파일 서빙도 `do_GET`
안에 있다. multipart 업로드 파서(`_read_upload`)를 손으로 쓴 이유는 `cgi` 모듈이 Python 3.13 에서
제거됐기 때문이다 — 되돌리지 말 것.

### 페이지 번호 추적 (chunking ↔ parsing 불변식)

`parsing.parse_pdf` 는 페이지별 텍스트와 그것을 `"\n"` 으로 이어 붙인 `doc["text"]` 를 함께 준다.
`parsing.page_of(pages, offset)` 이 **전체 텍스트의 문자 위치 → 원본 페이지 번호** 를 되돌린다.
따라서 청킹 함수는 조각의 텍스트뿐 아니라 **`doc["text"]` 안에서의 시작 오프셋**을 끝까지 들고
다녀야 한다(`_mk(text, start, ...)`). 오프셋을 잃으면 검색 결과의 출처 페이지가 조용히 틀어진다.
새 청킹 전략을 추가할 때 가장 깨지기 쉬운 지점이다.

전략 네 가지(`fixed` / `structure` / `paragraph` / `semantic`)는 `chunking._FN` 에 등록되고
라벨은 `config.STRATEGIES` 에 있다 — 새 전략은 두 곳 모두 고쳐야 화면에 나온다. 전략 함수의
부름꼴은 `(doc, size, ctx)` 하나로 맞춰 두었다. `ctx` 를 보는 것은 지금은 `semantic` 뿐이고
나머지 셋은 받기만 한다. `_split_long`(상한 초과
덩어리 재분할, 짧은 꼬리는 앞에 붙임)과 `_merge_short`(목차 페이지에서 생기는 8~10자짜리 조각
수백 개를 이웃끼리 묶음)은 실제 문서에서 나온 문제를 막는 장치다. 오버랩은 의도적으로 없다.

#### 문장 (`chunking.split_sentences`)

문장은 **의미 경계 청킹이 자를 후보**이자 **근거 하이라이트가 칠할 단위**다. 한 앱 안에서
"문장"이 두 가지 뜻이면 화면이 설명되지 않으므로 정의를 한 곳에만 둔다. 경계는 두 가지다.

- 문장부호 뒤의 공백 — 언제나. 뒤에 공백을 요구해 `3.5` 나 `rev05.pdf` 에서는 끊기지 않고,
  앞이 `숫자.` 면 절 번호로 보아(`7.7. USB` 의 `7.7.`) 역시 끊지 않는다.
- 줄바꿈 — **빈 줄이거나 다음 줄이 번호·기호·대문자 제목으로 시작할 때만**(`_NEW_BLOCK`).

줄바꿈을 무조건 경계로 보면 안 된다. PDF 는 한 문장을 여러 줄로 끊어 주는 것이 기본값이라
`...requires processes / compliant with...` 처럼 문장 한복판이 경계가 되고, 의미 경계 청킹이
바로 거기서 자른다. 이 규칙을 넣어 같은 문서의 문장 수가 644 → 377 로 줄었다.

`_sent_merge_short` 는 **앞 조각이 하한(`config.SENT_MIN_CHARS`)에 못 미칠 때만** 잇는다.
짧은 쪽을 볼 때마다 이으면 이미 긴 조각이 뒤따르는 짧은 문장들을 계속 삼켜 문단 하나가
통째로 한 덩어리가 된다. 하한이 한국어 한 문장(대개 25~35자)보다 크면 멀쩡한 문장끼리 붙는다.

#### 의미 경계 (`chunking.chunk_semantic`)

앞의 세 전략은 글의 모양만 본다. 이것은 뜻을 본다 — 문장을 벡터로 바꾸고 이웃한 두 문장
사이의 코사인 거리를 재, **거리가 상위 N% 인 자리**에서 자른다. **임베딩을 부르는 유일한 청킹
전략이다**(`llm.embed_many`, `llm.cosine`). 자르는 자리를 절댓값이 아니라 백분위로 정하는 이유는
거리의 절댓값이 문서마다 달라서다 — 고정 임계값을 쓰면 어떤 문서는 한 번도 안 잘리고 어떤
문서는 문장마다 잘린다.

`sentence_distances` 가 잰 거리는 `web.STATE["sem_cache"]` 에 남는다. **백분위만 바꿀 때는
임베딩을 다시 부르지 않는다** — 자르는 자리를 옮기는 데 필요한 것은 거리뿐이고 거리는 이미
있다(실측: 처음 2.5초, 그 뒤 3밀리초). 벡터 자체는 버린다. 거리를 얻고 나면 (문장 수 × 1536)
개의 숫자를 쥐고 있을 이유가 없다. **문서가 바뀌면 이 캐시를 반드시 비운다**(`_api_upload`).
다른 문서의 문장 거리로 자르면 조용히 엉뚱한 결과가 나온다.

`size` 는 쓰지 않는다 — 조각의 길이를 정하는 것이 백분위이기 때문이다(화면에서도 길이 칸을
숨긴다). 다만 뜻이 좀처럼 안 바뀌면 한 묶음이 끝없이 길어지므로 `CHUNK_SIZE_MAX` 에서만 끊는다.
청크는 `doc["text"]` 의 연속된 구간을 그대로 잘라 낸 것이라 시작 오프셋이 문장 구간에서 바로
나온다 — 페이지 추적이 다른 전략과 같은 방식으로 유지된다.

### 외부 호출은 `lab/llm.py` 한 곳

SDK 없이 `urllib` 로 직접 부른다. **청크 원문이 외부로 나가는 유일한 지점이므로 다른 모듈에서
OpenAI 를 직접 부르지 말 것.** `_post` 가 429/5xx 에 지수 백오프로 재시도하고, `_explain` 이 상태
코드를 사람이 읽는 한 줄 한국어로 바꾼다(원문 JSON 을 그대로 띄우지 않는다).

- 생성: **Responses API** (`POST /v1/responses`) — `input` · `max_output_tokens` ·
  `reasoning: {effort: "none"}` · `store: false`. Chat Completions 가 아니다. 응답은
  `output[] → type=="message" → content[] → type=="output_text"` 를 이어 붙여 읽는다.
  `_STATE["temperature_ok"]` 는 모델이 `temperature` 를 400 으로 거부하면 그 뒤로 빼고 보내는 장치다.
- 임베딩: `POST /v1/embeddings`, `dimensions` 를 명시, 100개씩 배치, 빈 문자열은 `" "` 로 치환
  (API 가 거절한다), 응답을 `index` 로 재정렬해 순서를 보장한다.
- 로그확률: 생성 호출은 전부 `respond()` 를 지나고, `generate()` 는 글자만 돌려주는 껍데기다.
  `respond(..., top_logprobs=N)` 이 토큰별 후보와 로그확률을 함께 받아 온다(LLM 재정렬이 쓴다).
  **`top_logprobs` 만 보내면 `logprobs` 가 빈 칸으로 온다** — `include:
  ["message.output_text.logprobs"]` 로 따로 청해야 실려 온다(실측). 둘은 한 벌이라 모델이
  거절하면 함께 뺀다. `_unsupported` 가 400 이 가리키는 설정을 `_STATE` 에 적어 두고 그 뒤로
  보내지 않는 장치이며, `temperature` 도 같은 자리에서 다룬다.

**질문과 문서는 반드시 같은 모델·같은 차원으로 임베딩한다.** `config.EMBED_MODEL` 이나
`EMBED_DIM` 을 바꾸면 기존 `chroma_db/` 와 섞이므로 먼저 `store.reset()` 해야 한다.

### 저장소 (`lab/store.py`)

Chroma 의 기본 임베딩 함수를 쓰지 않는다(모델을 내려받지 않기 위해). 벡터는 우리가 계산해 넣는다.
거리 기준은 `hnsw:space = cosine` 이고 `query()` 가 `1 - distance` 를 유사도로 돌려준다.
생성된 근거의 ID 는 `"gen#{시각}"` 이라 문서 조각과 겹치지 않고, 같은 질문을 다시 물어도
앞의 기록을 덮어쓰지 않는다. 문서 조각의
ID 는 `"{문서명}#{청크번호}"` 라서 같은 문서를 다른 전략으로 다시 적재하면 ID 가 겹친다 —
전략을 바꿔 비교할 때는 적재 전에 초기화한다. 메타데이터(문서명·청크번호·페이지·전략·글자수)는
검색 결과에 출처를 붙이기 위한 것이므로 적재 시 빠뜨리지 말 것.

### 질의 재작성 (`lab/rewrite.py`)

검색 앞에 붙는 **선택 스위치**(`/api/search` 의 `rewrite: true`, 기본 끔)다. 사람이 묻는 말과
문서에 쓰인 말이 달라서 생기는 문제를 다룬다 — "소프트 에러가 뭐야?" 로는 `soft error` 라고
적힌 영문 문서와 낱말이 하나도 겹치지 않아 BM25 가 0건이 된다.

**검색에는 바뀐 질의를, 답변에는 원래 질문을 쓴다.** `pipeline.search` 에서 `search_q` 는
임베딩과 BM25 에만 들어가고(`llm.embed_one(search_q)`, `bm25.search(..., search_q, ...)`),
`answer_mod.answer(q, ...)` 에는 원래 질문 `q` 가 간다. 바꾼 질의로 답까지 만들면 사용자가
묻지 않은 것에 답하게 된다 — **여기에 `search_q` 를 넘기지 말 것.**

모델에게 `store.status()` 의 문서 목록을 함께 준다. 그 문서들에 쓰일 법한 용어를 고르라는
뜻이지 문서를 지정하라는 뜻이 아니다. 프롬프트가 금하는 것은 네 가지다 — 없는 조건·수치,
질문에 대한 답, 문서 이름·번호, 설명이나 따옴표.

**모델이 규칙을 지켰는지는 기계로 확인한다**(`_check`). 적어 두는 것만으로는 안 지킨다는
보장이 없고, 질의는 검색 결과를 통째로 좌우한다. 원문에 없던 숫자가 들어왔거나 길이가
터무니없으면(원문의 4배 또는 120자 초과) **바꾼 질의를 버리고 원문으로 검색한다.**
숫자 검사가 문서 번호까지 걸러 내므로 프롬프트에서도 문서 이름·번호를 금해 둘을 맞춰 놓았다.

`rewrite()` 는 **예외를 올리지 않는다.** 호출이 실패해도 검색은 계속되어야 하고 그때 쓰는 것은
원래 질문이다. 왜 못 썼는지는 `note` 에 담아 화면이 알린다 — 조용히 원문으로 넘어가면
사용자는 무엇으로 검색됐는지 모른다. 화면(`#rewrite-box`)은 언제나 **원래 질문 · 실제 검색
질의 · 적용 여부**를 나란히 적고, 적용됐을 때만 파란 테두리를 준다.

기존 검색 방식은 그대로다. 두 열(의미·BM25)도, K 도, 근거 하이라이트도 손대지 않았다 —
바뀌는 것은 두 검색에 들어가는 문장 하나뿐이다.

### HyDE (`lab/hyde.py`)

검색 앞에 붙는 **선택 스위치**(`/api/search` 의 `hyde: true`, 기본 끔). 질문과 문서는 생김새가
달라서 — 질문은 짧고 의문형, 문서는 길고 서술형 — 벡터 공간에서도 떨어져 있다. 모델에게
"문서에 이렇게 쓰여 있었을 것"이라는 문단을 쓰게 하고 **질문 대신 그 문단을 임베딩해** 찾는다.
문서끼리 견주는 셈이 된다.

**가상 답변의 내용이 맞는지는 상관없다.** 우리가 쓰는 것은 그 글의 *벡터*이지 주장이 아니다.
그래서 세 가지를 지킨다 — 화면에 "검색용 추측"이라고 밝혀 보여 주고, **답변의 근거로 쓰지 않고,
저장소에도 넣지 않는다**(검색이 끝나면 버린다). 이 셋 중 하나라도 어기면 모델의 추측이 문서
근거인 척하게 된다.

적용 범위는 **의미 검색(왼쪽 열)뿐**이다. HyDE 는 이름 그대로 임베딩을 바꾸는 방법이고,
BM25 에까지 가상 답변을 넣으면 질문에 없던 낱말로 찾게 되어 두 열을 비교하는 뜻이 사라진다.
초안은 **원래 질문**으로 만든다(재작성한 검색어가 아니라) — 답을 흉내 내는 글이므로 사용자가
물은 문장이 들어가야 한다.

`draft()` 는 예외를 올리지 않는다. 실패하면 질의 그대로 검색하고 왜 못 썼는지를 `note` 에 담는다
(`lab/rewrite.py` 와 같은 규칙이다). 길면 `HYDE_MAX_CHARS` 에서 자른다 — 문서 여러 장만 한 글을
임베딩하면 벡터가 여러 이야기로 뭉개진다.

### LLM 재정렬 (`lab/rerank.py`)

검색 **뒤**에 붙는 **선택 스위치**(`/api/search` 의 `rerank: true`, 기본 끔). 검색은 질문과
조각을 따로 잰다 — 임베딩은 각자 벡터로 바꿔 거리를 재고 BM25 는 낱말이 겹치는지를 센다.
둘 다 질문과 조각을 나란히 놓고 읽은 적이 없다. 재정렬은 그 둘을 한 프롬프트에 같이 넣어
모델에게 직접 묻는다.

**후보를 K 개보다 넉넉히 꺼내 온다.** `pipeline.search` 가 `pool = min(k × RERANK_POOL_MULT,
RERANK_POOL_MAX)` 로 검색을 돌리고(두 열 모두), 판정이 그중 K 개를 고른다. K 개만 꺼내 다시
줄 세우면 순서만 뒤바뀔 뿐 **원래 순위로는 화면에 못 오던 조각을 끌어올릴 수 없다** — 그것이
재정렬의 값어치다. 조각 하나가 곧 호출 하나이므로(두 열이면 2배) 상한을 둔다.

판정의 꼴은 `Y 0.92` **한 줄뿐**이다. 첫 글자가 Y(쓸모 있음)/N(없음), 한 칸 띄운 뒤가 이
조각이 쓸모 있을 확률이다. **첫 토큰이 곧 판정이어야** 그 자리의 로그확률을 쓸 수 있다 —
앞에 "판정:" 이 붙으면 재려던 자리가 사라진다. 지켰는지는 `_parse` 가 **기계로 확인한다**
(`lab/rewrite.py` 와 같은 규칙). Y 인데 확률이 0.5 미만인 것까지 잡아 화면에 적는다.

**순서는 첫 토큰의 로그확률로 정한다.**

    P(Y) = p(Y) / (p(Y) + p(N) + r)        r = 1 − (후보들의 확률 합)

모델이 적어 낸 숫자는 0.9 · 0.95 몇 값에 뭉쳐 열 조각을 줄 세울 수 없다. 로그확률은 촘촘하다.
`r` 은 **후보 목록에서 잘려 나간 몫**이다 — API 는 `top_logprobs` 를 20 으로 청해도 확률이 큰
후보만 보내, 모델이 확신하면 고른 토큰 하나만 온다. 그대로 두면 `p(N)=0` 이라 P(Y) 가 전부
1.0 으로 뭉치므로 남은 몫을 N 쪽에 보태 보수적으로 센다(실측: 0.999996 과 0.999863 이 갈림).
그래도 같으면 모델이 적은 확률로, 그마저 같으면 검색이 준 순서로 가른다.

로그확률이 오지 않으면 **모델이 적은 확률**로, 그것마저 없으면 **Y/N 만으로** 줄을 세우고,
무엇으로 세웠는지를 판정마다 `source` 에 남겨 화면에 적는다.

지키는 것:

- `rerank()` 는 **예외를 올리지 않는다**. 판정이 실패해도 검색 결과는 이미 있고 그때 쓰는 것은
  검색이 준 순서다. 판정 못 한 조각은 **점수를 지어내지 않고** 판정된 것들 뒤에 원래 순서대로
  둔다. 하나도 판정하지 못하면 `applied=False` 로 검색 순서를 그대로 쓴다.
- **판정에는 원래 질문을 쓴다**(재작성한 검색어가 아니라). 다듬느라 뜻이 좁아진 문장으로
  판정하면 사용자가 묻지 않은 기준으로 조각을 버리게 된다.
- **전후 순위를 함께 돌려준다**(`rows`). 밀려나 화면에서 사라진 후보까지 남긴다 — 무엇이 어디로
  갔는지가 안 보이면 재정렬이 무슨 일을 했는지 알 수 없다.
- 두 열을 **각각 따로** 재정렬한다. 같은 판정자를 서로 다른 후보 묶음에 들이대는 것이라
  두 열을 섞지 않는다는 규칙은 그대로다.
- `hits` 를 그 자리에서 고쳐 `rank` 를 1..K 로 다시 매긴다. **`pipeline.search` 에서 재정렬 뒤
  `hits`·`bhits` 를 다시 묶어 주는 것을 빠뜨리지 말 것** — 뒤따르는 근거 하이라이트와 답변
  생성이 이 이름을 쓰므로, 밀려난 후보가 남아 있으면 화면에 없는 조각을 임베딩하고 근거로 넘긴다.

### 생성된 답변을 근거로 되먹이기

답변 생성을 켠 채 `save_answer: true` 를 주면 **만든 답변을 임베딩해 저장소에 넣는다**. 다음
검색부터 그 글이 근거로 걸린다. HyDE 초안이 아니라 **문서 조각을 근거로 만든 최종 답변**만
넣는다(초안은 검증된 것이 없다).

이 기능은 저장소를 모델의 말로 물들일 수 있다. 실제로 그렇게 된다 — 같은 질문을 다시 물으면
직전 답변이 1·2위로 올라오고 문서 조각이 뒤로 밀린다. 그래서 **구분 장치가 기능의 일부다.**
하나라도 빼지 말 것:

- 저장 1건마다 `source` 가 붙는다(`document` / `generated`). **옛 기록에는 이 키가 없으므로
  없으면 `document` 로 읽는다**(`store._row`). 기존 저장소를 그대로 쓰기 위해서다.
- 생성분은 `document` 이름도 `config.GENERATED_DOC` 로 다르고, 어떤 질문에서 나왔는지
  (`question`)와 무엇을 근거로 삼았는지(`based_on`)를 함께 남긴다. 출처를 거슬러 갈 수 있어야 한다.
- 화면에서는 배지·카드 색·아래 출처 줄 **셋으로** 알린다. 색 하나에 기대지 않는다.
- `include_generated` 스위치로 양쪽 검색에서 뺄 수 있고, `store.clear_generated()` 가
  생성분만 지운다(문서 조각은 그대로). 전부 비우고 PDF 부터 다시 적재하지 않아도 되돌아간다.

**거르는 일은 Chroma 의 `where` 가 아니라 파이썬에서 한다.** 옛 기록에 `source` 키가 없어
`where` 로 거르면 원문 조각까지 통째로 사라진다. 넉넉히 받아 와 걸러 낸 뒤 k 개를 취한다.

`pipeline.save_answers` 는 **아무 답이나 넣지 않는다.** 꺼낸 조각이 없거나, 너무 짧거나,
"확인되지 않습니다" 라고 한 답은 건너뛴다. 그런 문장이 근거로 쌓이면 다음 검색에서
"확인되지 않습니다" 가 근거로 붙고 그 위에 또 답이 쌓인다. 두 열의 답이 글자까지 같으면
한 번만 넣는다. 저장하면 BM25 색인을 버린다(`bm25.invalidate()`).

### 근거 하이라이트 (`lab/evidence.py`)

검색 결과에 "왜 이 조각인가"를 붙인다. **임베딩 모델만 쓴다 — 생성 모델을 부르지 않는다.**
검색이 청크 단위로 한 계산을 문장 단위로 한 번 더 하는 것뿐이다: 뽑힌 청크를 문장으로
쪼개고(`chunking.split_sentences`), 질문과 같은 모델·같은 차원으로 임베딩하고,
코사인 거리를 잰다(`llm.cosine`).
하이라이트는 모델의 말이 아니라 거리 계산 결과다 — 이 성질이 이 방식을 쓰는 이유이므로
LLM 에게 "근거 문장을 고르라"고 시키는 식으로 바꾸지 말 것.

표시 기준선은 **질문 ↔ 청크 거리**(`hit["score"]`)다. 청크 벡터는 그 안의 문장들이 뭉뚱그려진
것이므로, 청크 전체보다 질문에 가까운 문장이 이 청크를 끌어올린 쪽이다(`high`). 가장 가까운
문장 하나는 기준선을 못 넘어도 표시한다(`top`). 어느 문장도 기준선을 못 넘는 일은 흔하다 —
질문이 여러 갈래일수록 청크 전체가 더 가깝게 나온다. 그때는 "조각 전체가 맞은 경우"라고
화면에 그대로 적는다(없는 근거를 지어내지 않는다).

문장 구간은 **청크 텍스트 안에서의 (start, end) 오프셋**으로 들고 다닌다. 화면은 이 오프셋으로
원문을 잘라 칠하므로 잃으면 엉뚱한 자리가 칠해진다 — 청킹의 페이지 오프셋과 같은 종류의
불변식이다. 내보낼 때 `_u16` 이 파이썬 코드포인트 오프셋을 브라우저(UTF-16) 기준으로 바꾼다.
BMP 밖 글자가 하나라도 섞이면 그 뒤가 통째로 밀리기 때문이다.

`/api/search` 의 `highlight` 스위치다(기본 켬). 켜면 임베딩 호출이 한 번 더 나간다 —
뽑힌 조각의 문장 전부를 한 배치로 보낸다.

### 낱말 검색 (`lab/bm25.py`)

검색 화면은 **같은 질문을 두 방식으로 돌려 나란히 보여 준다**. 왼쪽이 의미 검색(임베딩),
오른쪽이 BM25(낱말)다. **둘을 섞지 않는다** — 점수를 합치거나 한쪽을 골라 주면 무엇이
무엇을 찾았는지가 화면에서 사라지고, 이 앱이 보여 주려는 것이 바로 그 차이다.

외부 호출이 없다. 표준 라이브러리로 BM25 를 직접 계산한다(공식은 모듈 docstring 에 있고
`k1`·`b` 는 `config` 에 있다). **말뭉치는 `store.all_chunks()`, 즉 의미 검색과 같은 저장소다** —
말뭉치가 다르면 나란히 놓고 비교하는 뜻이 없다. 색인은 만들어 두고 다시 쓰며
(`bm25.invalidate()`), 적재(`_api_embed`)와 초기화(`/api/reset`)에서 반드시 버린다.

한국어는 조사가 붙어 다녀("소프트에러는") 띄어쓰기만으로는 질문의 "소프트에러"와 맞지 않는다.
형태소 분석기를 넣는 대신 **한글은 두 글자씩 겹쳐 쪼갠다**(소프/프트/트에/에러). 검색 엔진이
CJK 에 흔히 쓰는 방법이고 사전도 의존성도 필요 없다. 영문·숫자는 낱말 하나로 센다.

각 결과에 어느 낱말이 얼마나 보탰는지(`terms`)와 본문에서 칠할 자리(`segments`)를 함께 준다.
**BM25 쪽에는 임베딩 하이라이트를 걸지 않는다** — 맞은 낱말이 곧 이유라서 임베딩을 또 부를
이유가 없다. 두 열이 각자의 말로 근거를 대는 것이 이 화면의 짜임이다.

**BM25 점수는 0~1 이 아니다.** 상한이 없고 같은 질문 안에서만 뜻이 있으므로 왼쪽 열의
유사도·거리와 숫자를 직접 견주면 안 된다. 화면의 막대도 절댓값이 아니라 가장 크게 보탠
낱말 대비 몫으로 그린다.

한국어 질문으로 영문 문서를 찾으면 BM25 는 0건이 나온다. 버그가 아니라 이 방식의 성질이고,
화면은 그 사실을 문장으로 적는다(왼쪽은 같은 질문으로 찾아낸다). 이 대비를 지우지 말 것.

### 생성 (`lab/answer.py`)

`PROMPT` 의 지시는 세 가지다 — 준 근거만 쓴다 / 없으면 "문서에서 확인되지 않습니다" / 쓴 근거를
`[근거 1, 3]` 형식으로 밝힌다. 검색 결과가 비면 모델을 부르지 않는다. 질의 재작성을 켰더라도
프롬프트에 들어가는 질문은 **사용자가 쓴 원문**이다(위 `lab/rewrite.py` 참고). 답변 생성은 검색에서
**선택 스위치**(`/api/search` 의 `answer: true`)다 — 어떤 조각이 뽑혔는지 먼저 보고 켜는 순서를
의도한 것이므로 기본값으로 켜지 말 것.

켜면 **두 검색 결과로 각각 한 번씩, 모두 두 번 생성한다**(생성 호출 2회). 프롬프트는 같고
근거만 다르다 — 꺼내 온 조각이 다르면 답이 달라진다는 것을 같은 화면에서 보이려는 것이므로
한쪽으로 합치지 말 것. 실제로 갈린다: "What is 1 FIT?" 에서 BM25 쪽은 정의를 답하고 의미 검색
쪽은 "문서에서 확인되지 않습니다" 를 답하는 일이 일어난다.

### 화면 (`static/`)

빌드 단계 없는 바닐라 JS. 탭 네 개가 `HAVE {doc, chunks, store}` 로 앞 단계 완료를 표시하지만
이동을 막지는 않는다(`gate()`). 청크 카드는 문서가 크면 천 장이 넘으므로 `PREVIEW_STEP`(40) 씩
이어 붙인다 — 전부 그리면 브라우저가 멈춘다.

④ 검색은 `.duo` 두 열(좁은 화면에서는 위아래)이고 `renderColumn(key, ...)` 하나가 양쪽을 그린다.
`chunkNode` 는 두 열이 함께 쓰므로 점수 이름을 `extra.scoreLabel` 로 받는다(유사도 / 점수).
`whyNode` 는 `why.terms` 가 있으면 낱말 표를, 없으면 문장 표를 그린다.

재정렬을 켜면 세 군데가 함께 붙는다 — 위쪽 `#rerank-box`(판정의 꼴과 줄 세운 값), 열마다의
`#rr-{key}` 전후 순위 표(밀려난 후보는 회색 줄로 남긴다), 조각 카드의 `rrNode`(모델이 적은
한 줄 · 첫 토큰 · 후보 · P(Y) 셈). 셋 다 있어야 "왜 이 순서인가"가 설명된다.

점수 막대는 `.bar > .fill` 인데 **`.bar` 는 상단 헤더 띠도 쓰던 이름이라** 헤더 규칙의
`padding` 이 막대 높이를 밀어내 속이 비어 보였다. 헤더 쪽을 `.band-brand .bar` 로 좁혀 두었다 —
전역 `.bar` 로 되돌리지 말 것.

## 설정

포트·모델·청킹 기본값·한계값은 전부 `lab/config.py` 에 모여 있다. 화면에서 고르는 것(전략·청크
크기·K)만 예외다. `config.api_key()` 는 환경변수를 먼저 보고, 없으면 프로젝트 루트 `.env` 를
`utf-8-sig` 로 직접 파싱한다(python-dotenv 의존성 없음).
